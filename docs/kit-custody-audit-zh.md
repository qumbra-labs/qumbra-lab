([#483](https://github.com/qumbra-labs/qumbra-lab/issues/483);规范:

易所、托管方或机构——以及接收端的审计方或监管方。先例形态是 Circle 的机
构级 **USDCx on Aleo**:用协议原生 view key 承载 AML/审计可见性
([aleo.org](https://aleo.org/post/aleo-view-key-compliance/))——迄今为止
对"常设的密钥级披露正是合规实际接受的东西"最强的机构背书
(`auditable-privacy.md` §3)。技术细节以英文版为准;行号基于 lab `main`
`cf15b11`。

**先划范围**:本文讲的是交易所(或任何机构)**自己的钱包**——充值台、金
库、冷托管——如何向其选定的一方开放常设审计。它*不*涉及充值用户:到达的
充值由披露信封逐笔筛查(工具包的边缘层——`crates/qlab-vask/README.md`),
不需要任何人交出常设密钥。

## 1. 密钥阶梯——可交出的东西有哪些

Qumbra 的披露栈是密钥级的:资金池均一,链上没有任何东西标记一个被审计的钱
包,而下面每一项能力都在参考钱包中**于类型层面**强制
(`qlab-wallet/src/viewing.rs:8-12`;"不能"一栏由 `compile_fail` 文档测试
锁定为编译错误,不是靠约定):

| 密钥 | 持有 | 能 | 不能 |
|---|---|---|---|
| 花费密钥(`Wallet`/`SpendingKey`) | `sk` | 一切,包括花费 | — |
| **完整查看密钥 `Fvk`** | `nk`、`div_seed` | 检测+解密全部入账;**看到花费**(推导 `nf`);推导 `rkm(d)`;生成该钱包的地址 | 花费 |
| **入账查看密钥 `Ivk`** | 仅 `div_seed` | 检测+解密入账;枚举该钱包的 diversifier 槽位用于扫描 | 看到花费;生成地址;花费 |
| 分散化解密密钥 `dk_d` | 单一 diversifier 的 ML-KEM 密钥 | 在**单个地址槽位**检测+解密入账 | 其余一切 |

`Fvk::to_ivk` 是单向降级——`nk` 被丢弃且不可恢复(`viewing.rs:94`)。自
issue #32 起,地址*生成*是 `Fvk` 能力而非 `Ivk` 能力(`viewing.rs:17-27`):
`Ivk` 持有者能扫描交给它的地址,但不能为该钱包铸造新地址。

## 2. 常设 fvk 给审计方看到什么——以及看不到什么

把某托管账户的 `Fvk` 交给审计方,对方将持续地、覆盖该账户**过去与未来的全
部历史**得到:

- **每一笔入账 note**:检测加上 104 B note 明文的完整解密——金额,以及能
  重算链上 commitment 的打开材料,因此金额是对照共识数据核验的,不是被审
  计方自报的。
- **每一次花费事件**:`Fvk` 能推导所持每张 note 的 nullifier
  (`viewing.rs:87`),并与按块服务的 nullifier 集合比对
  (`GET /v1/nullifiers`,#314 的线格式),因此它看得到托管资金*何时*移动、
  动了哪些 note。
- **找零与余额演化**:找零输出回到本钱包、以入账形式可见,因此每个高度上
  的可花余额都可重建——这正是金库审计与持仓证明的用途。
- **地址关联**:`Fvk` 能对每个 diversifier 推导 `rkm(d)`,因此该账户所有
  分散化地址*对审计方*互相可关联(这正是审计的意义;对其他所有人它们保持
  不可关联,PR #35)。

它**不**给出的,与上面同样直白地陈述:

- **出账的收款方与逐收款方金额。** Qumbra 没有出账查看密钥(ovk)机制:出
  账支付的输出 note 加密给*收款方*的密钥,链上根本不携带收款方身份(钱包
  自己的历史功能正因为这一点需要本地 `sends.v1` 记录——lab PR #324)。持
  有常设 fvk 的审计方看到的是:高度 h 有 N 张 note 共计 X 离开托管、找零
  回来多少——即流出台账——而不是付给了谁。需要收款方级答案的审计制度用
  **选择性**层:本工具包所验证的同一种披露证明信封,由持有全部 witness 的
  发送方逐笔生成。
- **任何其他钱包的任何信息。** fvk 的作用域是一个账户的密钥树;从它到整个
  资金池没有任何路径。
- **花费权。** 无论如何被攻破,fvk 都不能动资金——fvk 泄露的爆炸半径是该
  账户的*隐私*(整段历史,含追溯),而绝不是它的钱。相应地对待 fvk:按受
  监管记录级的敏感材料处理,不是随手的 API 凭证。

## 3. 作用域与轮换

- **按 HD 账户划定作用域,绝不按种子。** 主种子的每个账户是独立子钱包,拥
  有自己的 `nk`、`fvk`、`ivk` 与 diversifier 树
  (`qlab-wallet/src/viewing.rs:185-192`;格式:
  `qumbra-design/wallet-interop-spec.md` §5)。披露受审计账户的 fvk——交
  出账户层级之上派生的任何东西(更不用说种子助记词本身)等于披露现有与未
  来的所有账户。
- **对过去的披露不可撤销。** fvk 能解密该账户自建立以来的全部历史,事后没
  有任何办法收窄(`auditable-privacy.md` §5 的追溯性论点在这里双向成立)。
  因此"撤销"审计方意味着**轮换**:开新账户、把托管迁移过去,让已披露账户
  的前向可见性自然衰减为零。从第一天就把轮换计入托管设计——它只是一个 HD
  索引,不是一次迁移。
- **一台一钥。** 充值台、热金库、冷托管应是不同账户,让每个披露安排对应一
  个运营面,单个 fvk 泄露的代价被限定为一个台面的历史。

## 4. 充值台需要的比 fvk 少

充值入账只需要检测并解密**入账** note——仅此而已。那是 §1 阶梯中的 `Ivk`
一行,或者更窄的单 diversifier `dk_d`。已交付的入账参考实现就是先例:
`qumbra-credit-ref` 的 `ExchangeKeys` 恰好持有一把分散化 `dk` 加地址
commitment(`qumbra-credit-ref/src/lib.rs:77`),并且其自身文档声明了
devnet 级捷径——密钥文件在进程内由种子派生(`src/main.rs:1-20`),这在
devnet 可接受,**不是**生产形态。生产:

| 面 | 主机上的密钥材料 | 绝不上主机 |
|---|---|---|
| 入账服务/充值台 | `Ivk`(或按槽位 `dk_d`) | `nk`、`sk`、种子 |
| 面向第三方的审计通道 | 受审计账户的 `Fvk` | 种子、其他账户的密钥 |
| 资金移动 | `sk`,置于冷托管/签名仪式 | — |

边缘主机被攻破时,`Ivk` 泄露的是入账充值历史——糟糕,但严格小于 fvk(无
花费可见性、不能铸地址),更与花费密钥不同类(没有资金风险)。阶梯的存在
就是为了让暴露面持有够用的最小密钥;用它。

## 5. 审计通道的运营

- **审计方像任何钱包一样扫描**:compact-block 线格式
  (`wallet-interop-spec.md` §2)原样服务共识数据;服务器知道请求方的 IP
  与拉取模式,永远拿不到密钥。若审计方连"它在审计某账户"这一事实都不能暴
  露,应自建节点,或经 Tor 加诱饵拉取扫描——§2 的信任姿态缓解措施对审计
  方与对钱包同样适用。
- **核验是原生的。** fvk 解密出的一切都对照链上已承诺数据重算(扫描中重算
  `cm`,nullifier 来自服务的集合),因此审计结论可对照共识核验,而不是被
  审计方的"信我"导出。这正是常设密钥审计强于报表式审计的性质——被审计方
  无法策展密钥所见。
- **确认口径**:审计台账应在最终性处记账,与入账同一条规则
  (`docs/kit-confirmation-policy.md`)。
- **文书**:披露协议应写明账户作用域(一把 fvk = 一个账户)、§3 的追溯性
  事实、轮换程序,以及密钥本身的处理等级。这些都不是协议;都是 USDCx 先例
  所常态化的内容。

## 6. 诚实的边界

- **EU AMLR**(2027-07-10 起适用)目前对匿名增强币的定义宽到不论有无查看
  密钥安排都会命中可选隐私设计;常设披露能否换来豁免,取决于尚未定稿的
  AMLA 技术标准(`auditable-privacy.md` §6)。本文的安排是对机构行之有效
  的东西(那边 §3 的证据表);它不是任何司法辖区的法律意见。
- **`Ivk` 与逐笔证明之间的粒度刻意留空。** 没有"出账查看密钥",也没有限时
  fvk;若某制度需要比常设更窄的出账可见性,答案是逐笔的选择性披露证明——
  本工具包已经在验证的那种——而不是新的密钥类别。这个留空是设计决定
  (`auditable-privacy.md` §8),记在这里,免得有人卖出密钥交付不了的审计
  范围。
