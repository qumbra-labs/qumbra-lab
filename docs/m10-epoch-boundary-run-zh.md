# 本地跨 epoch 边界浸泡 —— LOCALHOST/DOCKER 运行文档

> [English](m10-epoch-boundary-run.md)

> **范围标签:LOCALHOST/DOCKER。不作任何 WAN 延迟层面的主张。** 这次运行的存在只为跨过一条特定的线——**1,152 块的委员会 epoch 边界**——并把其余变量尽可能按住不动。WAN 侧的测量(真实 RTT、WAN 步调下的 LWMA、≥48 小时)属于 Phase B-WAN([#64](https://github.com/qumbra-labs/qumbra-lab/issues/64)),此处不主张。

> **⚠️ 出处警示,放在最前面,因为它是这次运行最弱的地方。** 本次浸泡由 **coordinator** 启动、采样并撰写——而它同时是将要对结果下判决的那个角色。**这正是 `qumbra-deploy/OPERATOR.md` R1 为 T-ops 设立的独立性规矩所要防止的情形。** 它起于 2026-07-26 00:24,早于 T-ops 角色存在,事后也未移交。**请把它的结论读作"协调者自产",而非独立验证。** Phase B-WAN 那次运行不存在这个缺陷。

## 这次运行为什么存在

委员会 epoch 是 **1,152 块**(`EPOCH_LENGTH_BLOCKS`,FROZEN v1.0)。边界处 epoch 机制要干真活:分级成员变更生效、名册为新 epoch 重新封存、保留 per-epoch 历史以便滞后的 checkpoint 对着正确的委员会验证、以及停机 jail 窗口重置。

**从来没有任何活体多节点网跨过一次。** 此前对这套机制的每一次行使,要么是单元测试,要么是用加速的 `SIM_EPOCH_LENGTH_BLOCKS` 做的进程内模拟;真实的 1,152 边界从未被一张运行中的网触及——Phase B-lite 停在 tip 388,T0-5 的 docker 浸泡停在 245。

有两点让它值得先在 localhost 上做,而不是等 WAN 那次跑在约 24 小时处跨过同一条线:

1. **隔离。** 在 WAN 上,边界处的异常可能是 epoch 机制,也可能是网络。在这里,它只可能是机制。
2. **调试地点。** 在这里发现的缺陷离一次 `docker exec` 只有一步;同一个缺陷在四大洲运行 24 小时后被发现,则不是。

**它的代价写在协调者 playbook 里,而且不小**:它占用开发机约 22 小时,期间三根已完成的棒在后面排队。这个取舍在 00:24 是对的、14:00 仍站得住、**而在 17:00 队列变深时本应重算**——那里记录的定性是**"不是浪费,是定价错误"**。

### 每次采样都武装的 STOP 检查

- 任一节点的 finality **回退**;
- 四个节点报告**不同的 `epoch` 值**(名册视图分裂);
- 某个节点静默;
- 以及跨越本身——任一节点报 `epoch ≥ 1` 时记录。

## 截至 22:20 的观察(264 次采样,tip 1146 / 1152)

**零告警。没有任何一次采样触发过 STOP 检查。**

### 难度已收敛,而其余现象都由它带动

`diff` 从 256 爬到约 3,200–3,700 后在该区间震荡。这是 LWMA 在正常工作:genesis 难度被刻意设得远低于 75 秒目标,所以早期区块以秒计到达,算法用了最初几小时做修正。

### finality 保持后跳跃 —— 有界,不发散

全程 `stall`(= tip − final)分布——**取本次运行全部 277 次采样中 node0 的读数**:

| stall | 采样数 |
|---|---|
| 1–8 | 155 |
| 9–16 | 83 |
| 17–24 | 35 |
| 26–33 | 4 |

> **2026-07-28 更正过两次,而第二次才是有教益的那次。** 原表是 146/76/30/4(合计 256),纯属错误:没有任何节点、任何前缀、也没有四节点合计能产生它。第一次修正得到 146/80/34/4(合计 264)——它自洽,也与它引作佐证的"38 次 `Degraded`"自洽,**因为两者都是在本次运行的前 264 次采样上数出来的,而不是全部 277 次**。在提交进仓库的 `m10-epoch-boundary-soak.log` 上重数全量,得到上表;而 264 是**唯一**能复现那组中间值的前缀长度——正是这一点定位了口径错误。`stall` 从未取到 0 或 25,故分桶无遗漏。
>
> 一般性教训,与差点把 B″ 的 +51 KB 记到 D3 头上的是同一条:**一个数字带着它自己的口径,而数据增长时口径不会跟着长。** 把口径写在数字旁边——这就是本表标题现在写明"277 次采样"的原因。

观测最大值 **33**。形态是**振荡而非漂移**:stall 爬到十几或二十几,一次 finality 推进落地,随即掉回个位数。`regime` 在 277 次里有 **238 次为 `Final`**,而 **39** 次 `Degraded` **恰好就是** `stall > 16` 的那些采样——`DEGRADED_MODE_LAG_BLOCKS = 2 × cadence`。277 次双向逐条核对,**零例外**:本次运行里上报的 regime 不只是与阈值相容,而是阈值的忠实函数。且 `final` 全程一直在推进。

**这一条的意义超出本次运行。** T-ops 在 WAN 网上报告了同样的"保持—跳跃"模式,并询问它是否是 WAN 效应。**不是**:它在这里、在亚毫秒 RTT 的 localhost 上同样出现。机制在协议里,不在网络里——多个 checkpoint 槽并发累票(`try_checkpoint` 一次提议所有待定网格高度),谁先过 quorum 谁最终化,更低的槽随即被 `NotAdvancing` 否掉。**没有任何东西丢失**,因为 `set_finalized` 要求新头是旧头的后代:**最终化头是高水位,所以最终化 1120 就等于最终化了它以下的一切。** WAN 放大了这场竞速,并没有制造它。

## 🎯 跨越 —— 2026-07-26 22:29:27 +0800,第 266 次采样

**1,152 块的委员会 epoch 边界已跨过,此前没有任何活体多节点网做到过。**

```
node0  tip=1155  final=1144  stall=11  diff=3244  epoch=1  regime=Final
node1  tip=1155  final=1144  stall=11  diff=3244  epoch=1  regime=Final
node2  tip=1154  final=1144  stall=10  diff=3230  epoch=1  regime=Final
node3  tip=1154  final=1144  stall=10  diff=3230  epoch=1  regime=Final
```

**四项检查全部通过:**

1. **四个节点在同一次采样里都报出了 `epoch=1`。** 转换在一个 5 分钟采样间隔内完成(采样器无法分辨间隔内部的先后),且任何一次采样都没有出现名册视图分裂——那是武装着的 STOP 检查之一,它没有响。
2. **finality 挺过了边界。** 四节点 `final=1144`、`regime=Final`,并且**过线之后 `final` 继续推进**。
3. **全程零告警**——没有任何一次采样触发 STOP 检查(至运行结束共 277 次)。
4. **这次跨越不是安静的,而这正是有价值的部分。** 两次采样之前,网络还处在 `final=1120, stall=24–26`——finality 已挂起约 35 分钟。随后它推进到 1144,并在 stall 10–11 时跨过边界。**也就是说,名册重新封存与一次正在进行的票累积落在同一个窗口里,且没有干扰它。** 若这次运行是在平静区间进入边界,这个重叠根本不会被行使到。

最后这一点在跨越之前就写在本文档里,而它正是这次运行的价值高于"打一个绿勾"的原因:**边界时序缺陷恰恰会在重封与累积重叠处显形,而那个情形这次被测到了。**

### 边界之后的行为——已记录,本次运行完成

采样器继续跑到 **tip 1201**,于 23:24:28 自行停止,**277 次采样、全程零告警**。跨越之后的十二次采样里,四个节点的 `epoch` 都稳定在 1,且 finality 持续推进——最终状态 `tip=1201 final=1192 stall=9 regime=Final`,四节点一致。

值得一提的是,边界**之后**的 `stall` 比之前更低(个位数,而进入跨越时是 24–26)。**重新封存没有让 finality 变差。**
