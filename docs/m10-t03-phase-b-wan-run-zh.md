## 门槛,以及它按什么计时

门槛是 **≥ 48 h 连续**,而且**按网计时,不按观测者计时**:容器 07:43:0xZ 起,采样器 07:57:19Z 才起。中间那约 14 分钟不是缺口——它们是从容器日志恢复的,记录在 `qumbra-deploy/OPERATOR.md` §3。

**门槛已达成。** 以每台容器自身的 `StartedAt` 到从它归档到的最后一条 telemetry 计,四台的覆盖分别为 **48.05 / 48.01 / 48.03 / 48.06 h**——最小 **48.01 h**——且**重启次数为零**。归档是在过杆**之后**拉的,不是之前,所以证据文件本身就跨过了门槛;此处没有任何向前外推。

## 主记录是节点,不是采样器

本包建立在**节点自己的容器日志**之上,而非那个 5 分钟 SSH 采样器。这是个刻意的选择,而且它是承重的:采样器在运行中途**瞎了 10.15 小时**(见"观测缺口"),而容器日志一行没漏。

其中的论证已写成一份采纳的设计文档——[`qumbra-design/observability-and-evidence.md`](https://github.com/qumbra-labs/qumbra-design/blob/main/observability-and-evidence.md),其规则是:**证据是节点自己的、持久的、经归档的输出;看板永远不是证据。**

有两个细节让这份归档真正可用,而且都很容易漏掉:

- **`docker logs -t`。** `TELEMETRY` 行自身不带时间戳。没有 `-t` 就没有时间轴,归档无法与任何东西对齐。
- **同时抓 `RestartCount`。** `restarts=0` 才使这份归档成为**一条连续记录**而不是碎片。连续性就是门槛本身,没有别的东西能证实它。

那几次 tip reorg 是深度 1、发生在运行最初几分钟、finality 尚未追上之前——是预期中的 PoW 行为,不是 finality 事件。

## 真实 WAN 节奏下的两次 epoch 边界

委员会的 epoch 机制此前从未在一个活的多节点网上跨过边界。一次 48 h 的运行、24 h 的 epoch,会跨**两次**,而且两次都在归档里。

**epoch 0 → 1,在 `tip=1152`:**

|---|---|---|
| node2 | 2026-07-27 06:37:22 Z | 14:37:22 |
| node3 | 2026-07-27 06:37:33 Z | 14:37:33 |
| node0 | 2026-07-27 06:37:42 Z | 14:37:42 |
| node1 | 2026-07-27 06:37:50 Z | 14:37:50 |

**四台在彼此 28 秒内全部完成**,跨三大洲,无分裂的 roster 视图。

**epoch 1 → 2,在 `tip=2304`:**

| 节点 | 交接时刻(UTC) | 本地(+0800) |
|---|---|---|
| node2 | 2026-07-28 06:39:08 Z | 14:39:08 |

**四台在彼此 79 秒内全部完成。** node3 第一条 `epoch=2` 的采样已经读到 `tip=2305`——telemetry 节奏约 47 s,它是在边界之后一个块才采到的,边界仍然是 2304。

第二次比第一次更值得说,理由值得写明:它发生在**操作者并没有守着看**的时候,发生在一个已经连续运行 47 小时的网上,且不需要任何干预。第一次是被期待的;第二次是例行的。

> **在案更正。** 此次交接最初被报为 19:23 +0800,那是错的——19:23 只是下文那段观测盲区结束后的第一个**采样点**。归档给出的是 14:37。**实时视图把一个头条结论说错了,而归档是对的**,这是本包方法论最清楚的一个例证。

## WAN 节奏下的 LWMA / 出块

Phase B-lite 只见过 localhost 节奏。此处实测(node0,1,707 个间隔,目标 75 s):

```
mean 86 s   median 60 s   p90 172 s   p99 320 s   max 629 s
```

这是难度正在跟踪时围绕目标的普通 PoW 方差:均值高于目标(retarget 滞后),中位数低于目标,而尾巴长——泊松式过程本就要求如此。这里没有任何迹象表明 LWMA 在 WAN 节奏下失常。

## finality 节奏 —— 以及本次运行开出的一个 FROZEN 问题

finality 按 8 块的 checkpoint 节奏推进。实测(node0,191 次推进):

```
mean 901 s   median 673 s   p90 1802 s   max 3161 s      (名义 8 块 ≈ 690 s)
191 次推进中有 69 次跨越了不止一个 checkpoint(步长 16 / 24 / 32 / 40 块)
```

**中位数上委员会完全跟得上**——673 s 对名义 690 s。尾巴很重:三分之一强的推进是多 checkpoint 的补课。

后果是这个网有相当一部分时间处于 `Degraded`:

| | node0 | node1 | node2 | node3 |
|---|---|---|---|---|
| `Degraded` 采样占比 | 15.4 % | 15.4 % | 14.1 % | 15.2 % |
| max `stall`(块) | 40 | 40 | 42 | 41 |

对照 `DEGRADED_MODE_LAG_BLOCKS = 16`。stall 达到 16 等于连丢两个 checkpoint,而连丢两个约六分之一的时间会发生。

**16 是否定错、还是委员会在真实 RTT 下确实在抖,本次运行答不了**,而理由值得明说:**节点在丢 checkpoint 时什么都不发。** 整整 48 小时里 node0 只产出**十**行非 telemetry 日志,全部在启动时。没有 round 号、没有票数、没有超时原因、没有缺席名单。`stall` 计数器从 8 爬到 40 又落回来,中间那段是不透明的。

这个缺口就是 [issue #87](https://github.com/qumbra-labs/qumbra-lab/issues/87)。它不是锦上添花——它挡着一个 FROZEN 集合的决定,而在它关闭之前,**`DEGRADED_MODE_LAG_BLOCKS` 不得改动**。

### 一条确实成立的交叉核对

在四台合计 14,659 个归档采样中,`regime = Degraded` 与 `stall > 16` 在 **14,647** 个上吻合。十二个例外全是同一件事:**创世头**——`tip=0`、`final=-`、尚未有任何东西被最终化——每台节点在运行头 60 秒内各 3 条。这就是 [issue #73](https://github.com/qumbra-labs/qumbra-lab/issues/73),而本次运行把它量化了。**首次最终化之后,零例外。**

### 跨节点的 finality 一致性 —— 什么能证明、什么不能

四台最终停在同一个 `final`(2352),且任何节点的 `final` 从未减小。在这两个事实之间,它们会短暂地不一致:按 30 s 网格对齐后,四台在 `final` 高度上共有 **184 段分歧区间**,而且**全部收敛回完全一致**——中位 60 s,p90 150 s,最长 330 s,最大分歧 **40 块,恰好等于观测到的最大单次 finality 跃迁**。

这是采样相位对上跃迁式推进的特征,不是发散:每台约每 47 s 发一条 telemetry 且相位独立,而 finality 一次跳 8–40 块,所以相隔一个节奏采到的两台会跨在同一次跃迁的两侧。tip spread 表现相同——对齐样点中 4.9 % 超过 3 块,最大 8 块。

**诚实的边界:telemetry 不携带 checkpoint 身份**,所以本包能证明没有任何节点的 finality 高度回退、且四台总能重新重合,**不能**证明四台最终化的是**同一批** checkpoint。**高度一致不等于身份一致。** 这就是 [issue #84](https://github.com/qumbra-labs/qumbra-lab/issues/84),它是证据面的限制,不是关于这个网的发现。

## 观测缺口 —— 如实披露,以及为何它没有造成损失

那个 5 分钟采样器**并未**连续覆盖本次运行。两段缺口,均在操作者一侧:

| 窗口(+0800) | 时长 | 成因 |
|---|---|---|
| 2026-07-27 08:39:45 → 18:48:46 | **10.15 h** | 操作者出口 IP 轮换,而 SSH 安全组规则只放行一个已过期的 `/32`。22 端口是唯一对操作者开放的入站,所以这是瞬间、彻底的失明。窗口与一个工作日高度吻合。 |
| 2026-07-28 06:51:59 → 09:48:52 | **2.95 h** | 采样器进程随编辑器重启而死,随后又撞上同一个过期 CIDR 问题 |

采样运行的约 48 小时里,约 **13 小时未被采样器观测到**——约 27 %。

**两段窗口都从节点自己的日志中逐行恢复。** 那 10.15 h 的窗口:785 条 telemetry,一条不缺,tip 862 → 1353,finality 856 → 1344,18 % `Degraded`——与全程实测的 15.9 % 在统计上无法区分。黑暗里什么也没发生。

引用本包时请照此表述:**记录是完整的;实时视图不是。**

修复与教训记录在 `qumbra-deploy/OPERATOR.md` §3/§6:`admin_cidrs` 现在是列表(**地址只增不换**),以及*四台跨三大洲的主机不会同时挂——看起来同时挂时,怀疑它们共用的那条路径。*

## 本次运行不主张什么

- **四个场景演练不在本包内**:late-joiner sync、mining-node restart、2+2 分区 → 愈合、committee stall → recovery。它们欠着,而且是**刻意尚未跑**。
- **原因是镜像,不是排期。** 这四台跑的是 2026-07-26 构建的镜像。此后合并进 `main` 的有:[#79](https://github.com/qumbra-labs/qumbra-lab/pull/79)(把 block body 绑到 header —— 一处**共识正确性**修复)、[#82](https://github.com/qumbra-labs/qumbra-lab/pull/82)(D3 leaf-digest 绑定)、[#86](https://github.com/qumbra-labs/qumbra-lab/pull/86)(M11 peer discovery)。演练检验的是**当下的**设计,所以在这个镜像上取的演练证据描述的是一个已被取代的构建,将不得不重跑。
- **连续性主张不受此影响,而这个区分很要紧。** "某个真实构建无人值守连跑 ≥ 48 h、零重启、零 finality 回退"——这句话不会因为构建往前走而变弱。检验当下设计的演练没有这个性质。
- **四个里有一个今天根本跑不了** —— committee stall → recovery,理由见 finality 一节:节点恰恰对被测量的那个量沉默。
- 本包不对 NAT 后的参与者或敌意参与者作任何主张;这里每一台都是我们控制的、有公网 IP、入站 P2P 端口开放的主机。
- 本次运行的 telemetry 中**没有** `dialable=<n>/<known>`:M11 discovery 在镜像构建之后才合并。

2026-07-28 决定的顺序(`observability-and-evidence.md` §5.1、`OPERATOR.md` §4):**封存本包 → 做 #87 → 一次重部,携带 #79 + #82 + #86 + #87 → 然后跑全部四个演练。**
