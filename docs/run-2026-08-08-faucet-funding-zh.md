## 1. 本来要做的事

T1 faucet 持有花费钥匙，需要币。两条路：

- **(a)** 某台 fleet 主机把 `miner_rkm` 设成 faucet 的收款钥匙，替它挖；
- **(b)** faucet 主机自己跑一个矿工。

Larry 问哪个正确，并明确说不走捷径。选 **(a)**，三条理由，没有一条是"方便"：

1. **(b) 会改变这个网。** 它给刚跑完 §4 演练的四主机网加上第五个矿工，于是每一条演练结论
   都变成关于另一个拓扑的结论。
2. **(b) 把证明器放到热钥匙主机上。** 一次 grant 证明实测峰值 **11.89 GB**（lab PR #128），
   svc1 的 16 GB 规格就是为它定的。旁边再放一个矿工，会和派发路径抢它需要的内存，而失败
   模式是最糟的那种形状：faucet 跑着、表单能开、请求被接受，然后在派发那一步失败。
3. **§9.2 的规则可以推广。** "热钥匙绝不与任何它不需要的东西共享主机"——而 faucet **就是**
   一个持有热钥匙的钱包。

这部分很快就定了。然后执行它需要重启一台共识主机，而那才是有意思的部分。

## 2. 发现：这个网一直在零签名余量下运行

### 2.1 测到了什么

在四台 fleet 主机上采样已收盘的 `ROUND` 行。每一轮、每一台：

| 缺席的主机 | `have` | 对 `need=15` 的余量 |
|---|---|---|
| 任一 5 把钥匙的主机（node1/node2/node3） | 16 | **1** |
| **node0（6 把）** | **15** | **0** |

没有一轮采样达到 17。**每一轮恰好缺一台主机的钥匙段**，而是哪台在轮换。全程
`seen == have`、`variants=1`，所以这不是投票分裂。这是稳态——没有任何主机在滚动中，四台都健康。

### 2.2 为什么

`crates/qumbra-node/src/run.rs:2202-2206`，而且这是 `try_checkpoint` **唯一的**非测试调用点：

```rust
if self.mining && self.last_mine.elapsed() >= self.mine_interval {
    if self.try_mine() {
        self.try_checkpoint();
    }
}
```

`note_local_proposal` 只在 `try_checkpoint` 内部被调用。一台在该窗口内没挖到块的主机
**从不提案、从不签名、零票贡献**——它的钥匙在任何地方都缺席，包括它自己的账上。表现为每台
主机上反复出现的 `local=0` 轮次，且缺的正是该主机自己的钥匙段。

这是 lab #106 的第三条记录项。记录低估的地方：`CLAUDE.md` 和 PR #153 把这条耦合限定在
*"一个 `mining = false` 且持有钥匙的节点从不提案"*。在四矿工网上，它**持续降级每一台正在
挖矿的节点**。

### 2.3 存在两个机制，不能合并

- **(A) 结构性**——没挖到 ⇒ 整轮零票。
- **(B) 时延**——投了，但票在对端收盘前没到。slot 4040：node0 报 `local=6 seen=16`，
  node1 和 node3 在同一 slot 收盘时没有这六票（`absent=0..5`）。`quorum_ms` 实测
  **155–269 秒**每轮（属 #107 的范围）。

#106 的正文把其中之一读作 *"node3 的钥匙——慢，不是掉线"*。这对 (B) 成立，对 (A) 不成立，
而 (A) 是结构性的、一直在的那个。

### 2.4 运维后果

**任何单台主机重启都会让多数轮掉到法定人数以下。** 停一台 5 把的主机剩 16 把，再减去那一轮
静默的那台（5 或 6）⇒ 10 或 11 对 15。停 node0 剩 15，同样的论证给出 9 或 10。所以重启会
**在整个窗口内停摆终局性**，而不是闪断一下——这就是为什么选 node3（5 把，且在 12 轮样本里
本来就是最不稳定的签名者），而不是 node0。

🟡 这也意味着 §4 的 2+2 分区演练归因过窄：它的结论（两边都停摆）对，但"每边 11 和 10 把，
都低于法定人数"暗示是**分区**造成的。掉一台也一样。

**全程安全性完好**——同一 slot 上四台 `cpid` 完全一致、`variants=1`、`seen==have`。
#84 放在 `ROUND` 上的 `cpid` 一条命令就回答了这个问题，这正是它被造出来的用途。

已归档到 [#106](https://github.com/qumbra-labs/qumbra-lab/issues/106#issuecomment-5223333302)。

## 3. 交付了什么

svc1 从 `stopped` 一次走通到服务；`qumbra-faucet keygen` **在 svc1 上**运行，种子从未移动；
node3 的配置先用 `qumbra-node check` **对着候选文件、在不重启的前提下**验证，然后才换上并重启。

重启很干净——`RECOVERY restored snapshot at height 4073, replayed 0 records, resumed at tip
4073`。没有从 genesis 重新同步，**没有重演 #106 那次分叉**，这是 #104 的持久化和 #106
item (1) 的闸门在一次真实滚动上同时生效。约 2.5 分钟后落下一次新的 finalization，四台收敛到
`final=4072` 的 `fid=f411cd30c93e`（node1 落后一个 checkpoint 约 40 秒——那是滞后不是分裂：
分裂是*同一高度*上*不同*的 `fid`）。

发现两个缺陷：

- 🔴 **compose 的 entrypoint**——faucet 容器第一次 `up -d` 就 CrashLoop。同一形状的第三次；
  `docker-compose.svc-light.yml` 里已经为完全相同的失败写了注释。这个文件从没被执行过。
  已在 deploy PR #92 修复。那个看似顺手的"修法"（`command: ["faucet"]`）比崩溃更糟——
  那个分支是本机靶场路径，会往热钥匙主机上写 `mining = true`。
- 🟡 **`deploy.sh` 不生成 `miner_rkm`**——是顶着文件自己的"不要在主机上手改"横幅手加的，
  所以对 node3 再跑一次 deploy 会静默地断掉 faucet 的资金。未修复，记在 OPERATOR §9.6。

## 4. 我自己的错误，以及各自是被什么抓住的

这份记录里最有用的部分。三个，全都在被抓住之前已经发布或即将发布。

### 4.1 把索引列表当成计数的正则

`ROUND` 行里的 `voted=` 和 `absent=` 是**索引列表**。`voted=[0-9]+` 会从
`voted=0,1,…,15` 里匹配出 `voted=0`，读起来是*"这个节点投了零票"*——与事实恰好相反。
随后基于 `paste` 的多字段提取又在任何缺字段的行上整体错位。

**结果：** 一张干净、自洽、彻头彻尾错误的表，显示四台全是 `voted=0`，而我几乎据此得出了
该重启哪台的结论。

**是什么抓住了它：** 算术。`absent=16` 和 `have=16` 不可能同属一个 21 人名册的同一轮。
这些数字在任何人拿它们去对现实之前就已经加不拢了。

**规则：** 从字段提取推导任何东西之前，先读完整的原始行。每台自身的贡献字段是 `local=`。

### 4.2 从上下文而不是权威来源取主机地址

我用 `3.72.196.15` 去连 node2——那不是 node2，也不是这个 fleet 里的任何主机，是从早前上下文
带进来的陈旧地址。它超时了。**我在核对地址之前，就把它作为"node2 的运维通道断了"发到了
#106 上。**

**本该抓住它、却没有的东西：** `aws ec2 describe-instances` 在我查的**全部五个区域**里对这个
IP 都返回空。那是"主机有问题"的反证、"地址错了"的正证，而我读了过去。

**真正抓住它的：** 因为另一件事去读了 `terraform output hosts_file`。

**规则：** fleet 地址来自 `terraform output hosts_file`。已在
[后续评论](https://github.com/qumbra-labs/qumbra-lab/issues/106#issuecomment-5223384517)里公开撤回。

### 4.3 `gh` 解析到了错误的仓库

`gh issue comment 106` 从 **cwd** 解析仓库，而早前一次 `cd` 进 `qumbra-deploy/terraform`
还在生效。给 #106 的更正被投递到了 `qumbra-deploy`。它 404 了，因为那个仓库没有 #106——
**但它同样可能落在一个不相干的 issue 上。**

**规则：** 一律显式传 `-R qumbra-labs/qumbra-lab`。

### 4.4 三者共同的形状

每一个都是**一种看似合理的读法，因为没有任何东西逼它去对第二个来源，所以活了下来。**
§2 的那个发现是同一形状的反面：它在生产网上活了几周，是因为 `have=16 need=15` 看起来就是
一轮健康的收盘——只有把四台主机对**同一个 slot** 的看法并排放，结构才显形。

## 5. 顺序花了什么代价，又省下了什么

Larry 在 faucet 的 rkm 还不存在时就批准了重启 node3。立刻执行那个批准，换来的会是：一次停摆、
配置没变、之后还要再停一次——因为 `miner_rkm` 只能从一个当时还不存在的种子派生出来。

先查前置条件，把两次停摆变成了一次。**一个已获批准的动作，不构成跳过"它依赖什么"这个问题的理由。**
