# rig——它是什么、为什么串行、这里的绿到底证明什么

> [English](the-rig.md)（技术细节以英文版为准）
>
> 2026-08-03 应 Larry 之问("全套件在哪里跑,CI 还是 local?")而写。一句话答案:**local,就在这台机器上,在一把互斥锁下面**——这句话的每个分句都是花真金白银换来的。依据:`scripts/rig` 源码(77 行,全文读过)、`CLAUDE.md` §5(bench 纪律)、issue #64 的碰撞记录、2026-08-01 的同树事故,以及今天新添的一例。

## 1. "rig" 是什么

一个名字,三样东西:

1. **机器**——Larry 的 MacBook Pro(Apple M5 Max,18 核,36 GiB,macOS)。这个仓库历史上每一次验收套件、每一次证明尺寸复现、每一次 RSS 闸门测量都在这台机器上跑。bench 数字必须携带机器身份(bench 纪律第 2 条),因为离开机器身份的数字没有意义。
2. **互斥锁**——`scripts/rig`,一个 77 行的 bash 包装,核心是一次原子的 `mkdir`。
3. **纪律**——重活一次一个、全 workspace、串行,且锁**对所有人生效**,协调者也不例外。

## 2. 锁的机制(读源码得来,不是凭记忆)

```sh
scripts/rig run -- cargo test --release --workspace -- --test-threads=1
scripts/rig ps          # 在跑的 + 排队的 + 最近 5 次完成(退出码、日志路径)
scripts/rig log -f      # 实时跟当前持锁者的日志
scripts/rig status      # 持锁者一行版(输出稳定,供脚本用)
scripts/rig release     # 手动破锁——仅当 trap 没能触发时用
```

*(2026-08-05:每次 `run` 自动 tee 到 `~/develop/qumbra/logs/rig-<时间戳>-<pid>.log`,
等锁者在 `ps` 里可见而非静默排队,完成后追加一行进 `logs/rig-manifest.tsv`——
起止、owner、退出码、日志、命令。)*

- **锁是一个目录**:`~/.qumbra-rig.lock`(可用 `QUMBRA_RIG_LOCK` 覆盖)。抢锁就是 `mkdir`——POSIX 上是**原子**的,两个竞争者不可能同时成功。目录里放四个文件:`owner`、`pid`、`started`、`cmd`,所以 `status` 回答"谁/何时/在干嘛"不用猜。
- **等锁是轮询**:每 15 秒重试一次,首次等待和之后每 5 分钟打一行 "waiting for <owner>"。这就是为什么一个排队的套件可以合法地 50 多分钟没有任何输出——2026-08-03 实测:一个 wrapper 16:46 开始抢锁,17:38 才真正起跑 cargo。
- **持锁者身份**:`QUMBRA_RIG_OWNER`,否则 `MULTICA_ISSUE_ID`(所以 Multica 棒的锁会显示成它的 issue 号),否则 `user@host`。
- **僵尸锁自动收割**:持锁 pid 已不存在(`kill -0` 失败)时,下一个竞争者或 `status` 调用会自动破锁。没有这条,一根崩掉的棒会把 rig 卡死到有人发现为止——用脚本自己的注释说:"那比我们修掉的竞态更糟"。
- **释放靠 trap**,挂在 `EXIT INT TERM` 上——Ctrl-C 和 kill 都会释放。结束时 wrapper 打一行 `rig: command exited N`;**管道进 `tee` 的场合,以这行为退出码权威**(zsh 的 `$pipestatus` 和 bash 的 `$PIPESTATUS` 已经吃掉过一次报告的退出码捕获)。

## 3. 为什么是锁,不是约定

它取代的约定是"先看 `ps`,再去 issue #64 发 START 行"。那是 **check-then-act**,查和干之间的窗口是真实存在的:

- issue #64 记录了恰好从这个窗口里掉出来的**两次碰撞**——两根棒同时读到"机器空闲",相隔 56 秒先后开跑;另一次是协调者撞上了一根已经跑了六分钟的棒。
- **2026-08-02,一个测量读数是真实值的 2.1 倍**,因为一个套件从它底下开跑了。能发现,只是因为那根棒认得污染的长相。
- 讨论串自己的补救("在 `cargo test` 前一刻再查一次 `ps`")只是收窄窗口;`mkdir` 把窗口关死。

**issue #64 保留,但角色变成日志而非机制**——去那里记录跑了什么、花了什么,永远不是去那里要许可。

## 4. 为什么串行是硬约束,不是偏好

- release 套件在 36 GiB 的机器上**峰值 16–30 GB**。`qumbra-node` 里有**三个真 M3 prove 测试**;两个套件并跑不是慢,是死(或者更糟——悄悄给错数,见 §6)。
- 套件内部的 `--test-threads=1` 同理,是必需不是风格。长杆就是那几个 prove:2026-08-03 那趟里,单个测试 **973 秒**、**238 秒**,总时长 ~55 分钟。
- 完整验收在这台机器上的墙钟:**~20–55 分钟**,取决于树的大小和散热状态。把它算进预算;永远不要裁剪它(见 §5)。

## 5. 锁下面跑什么,绿了证明什么

验收栏(CLAUDE.md §5,有约束力):

```sh
scripts/rig run -- cargo test --release --workspace -- --test-threads=1
```

- **全 workspace,不过滤。** mode 过滤和 crate 过滤都被禁,两条禁令分别付过学费:过滤跑让一个陈旧的宽度 pin 漂了三个 session(PR #23 时代);PR #166 报了两个诚实的 crate 级绿,而 workspace 套件在**两个 crate 级跑都碰不到的第三个 crate 里**红了。
- **对账要念出声**:总数 = `main` 基线 + 你的新测试 − 你删掉的。负项也要验——`FAILED`(区分大小写)、`panicked at`、`^error` 全零。launcher 的 exit 0 不是套件的 exit 0。
- **什么是确定的、什么不是**:证明**尺寸**逐字节确定(直接断言;5/5 次一致是汇报惯例)。出证**时间**带 grind-PoW 抖动(±30–60% 属正常)——对包络判断,永远不要对单次差值报警。
- **陈述例外可以,悄悄跳过不行。** 纯 docs / 纯 shell 的 diff 结构上不可能让套件变红;把例外和它的差分证据写进验收评论(先例:PR #170)。

## 6. 污染与中断——实际观察到的失效模式

- **污染的长相**:`sys` 时间膨胀数倍而 instructions-retired 几乎持平 ⇒ 有别的东西在跑 ⇒ **丢弃这个数,不要加脚注保留它**。
  *(细化 2026-08-04,来自 mint-combo 棒的 b4 测量:`sys` 膨胀而 instructions-retired **上升**是另一回事——那是这台机器自己的内存压缩器在干真活(≥33 GB 级 footprint 会压出来),数是真的,只是机器在极限上;区分键是 instructions,不是 sys。)*
- **合盖会杀跑**(2026-08-03,验证过两次):合上 MacBook 盖子把一个套件杀在测试中间——日志断在半行,进程全无,锁随后被正确地按僵尸收割。部分套件结果毫无价值;规则是**从头重跑,覆盖日志**。
- **看的比被看的死得勤**——WAN sampler 四天死三次,而四台节点全程 `restarts=0`。同样的教训在 rig 尺度上:永远不要假设一个长命后台进程活过了没人看着的时段。查 `rig status` / 日志尾巴,不要查你"记得启动过它"的记忆。

## 7. CI 相对 rig 的位置

CI 存在,但**不是验收权威**。2026-08-01 的事故一句话说完:**CI 绿在 pre-merge head 上——那棵树不含后来弄坏合并树的冲突解决。**不同树上的绿,对正要合并的树不构成任何证据。

CI 的正当角色,同一天挣来的:解完冲突或合入 `main` 之后,**把合并树推回 PR 分支**,让 CI 在 rig 看到的同一棵树上重跑——这时它才是免费的第二道线,跑在别人的硬件上、和 rig 并行。那天五次同树对比完全一致(五棵树 1030 → 1051)。runner 成本与 SKU 的决策在 `docs/ci-runner-cost-decision.md`(§10 有 stop-usage 爆炸半径的账);CI 经济学以那份文档为准,不以本文为准。

## 8. 礼仪总结(整套协议就五行)

1. 每个重命令都走 `scripts/rig run --`——协调者的也一样。
2. 必须在 wrapper 外跑重活时,把它包起来:`scripts/rig run -- bash -c '…'`。
3. 排队是常态;等锁 50 分钟是系统在工作,不是卡死。
4. `rig status` 是活性检查;issue #64 是台账;两者不可互替。
5. 数字看着不对时,先怀疑机器再怀疑代码:污染、散热、电池、或一次睡眠——并且重跑,而不是推理。
