### 1. 🔴 The genesis auto-download needs a TLS client in the `qumbra-node` binary — and #297 argued the other way

The published URL is `https://seed.qumbra.org/genesis.qmb`, so "auto-download IF absent" means the node binary has to speak TLS. The only HTTP client in this tree that does is `qumbra_wallet::net` (rustls + webpki-roots under a hand-rolled HTTP/1.1). `qlab_cbserver::client::http_get` is plaintext-only, and `net.rs`'s own doc comment records why it was not given TLS:

> **This used to delegate to `qlab_cbserver::client::http_get`** and no longer can: that helper is plaintext-only and gaining a TLS stack would put rustls into `qlab-node`'s (and therefore the consensus node's) build graph.

**What I am building:** `qumbra-node` depends on `qumbra-wallet` (`default-features = false, features = ["net"]`) and `mine` fetches through `net::http_get`. My reading is that this honours #297 rather than reversing it — #297's concern was the **consensus library** graph (`qlab-cbserver` → `qlab-node` → everything), and this puts rustls in the leaf **binary** crate, which nothing depends on. The two binaries already ship in one tarball (#437), so the operator's install gains no new library either way.

**The counter-argument, stated fairly:** the deployed consensus node process now links a TLS client it did not link before, for one fetch, in one subcommand. And the security of that fetch does not rest on TLS at all — the artifact is hash-pinned, so a tampered download is refused by name whether it arrived over TLS or not.

**The fallback if you'd rather not:** `mine` keeps the pinned-hash verify and drops the fetch — genesis must already be in `DIR`, or `--genesis-url http://…` uses the plaintext client that is already in the graph. That is a materially worse "zero-to-mining in one command", which is why I'm defaulting the other way.

### 2. Task-book row that does not check out: "the tree already pins it"

The book says `expected_genesis_hash` "the tree already pins it". Verified: the pin exists **only inside a `#[cfg(test)]` assertion** — `genesis.rs`'s `genesis_hash_is_pinned` — plus a commented-out line in `qumbra-node.example.toml`, a doc comment, and `release-binaries.yml`'s `GENESIS_HASH:` env. There is no `pub const` any code can read, so `mine` cannot bake "the pin the tree already has"; it has to introduce one. I'm adding `mine::T1_EXPECTED_GENESIS_HASH` with a test asserting it equals `GenesisFile::new_devnet_t0().hash_hex()`, so the baked constant and the tree's own genesis construction cannot drift apart silently. Flagging it because the book's phrasing implies a smaller change than it is.

Same shape for the seeds: the four T1 addresses live in `docs/join-and-mine.md` and nowhere in code. Baking them means **a fleet address change is a rebuild** (or a `--seeds` override on the operator's side). That is what the book asks for and I think it's right for a defaults-in-the-binary command, but it is a new coupling and I'd rather name it now than have it surface at the next roll.

### 3. Where the auto-created wallet lands

The book says "if `DIR` holds no wallet". I'm putting it in **`DIR/wallet/`**, not `DIR` itself: `qumbra-wallet --dir DIR/wallet` then works verbatim for scan/backup/send, and the seed does not sit beside a `node.toml` an operator may well copy around or paste into an issue. To avoid ever generating a *second* wallet for someone who pre-made one the other way, the probe checks `DIR/wallet.seed` first and uses `DIR` when it is there. Say so if you'd rather it were flat in `DIR`.

### 4. What acceptance (a) can honestly assert

"node reaches mining with the derived rkm" — I can assert, in a test, that the written `node.toml` carries `mining = true` and a `miner_rkm` **byte-equal to the wallet kernel's own derivation**, and that the real binary's `check` preflights that config clean. I am **not** going to stand up a RandomX miner and wait for a block in a test on the shared rig. So the acceptance item lands as "the config the run path receives is the mining config, and it preflights" — one step short of the literal wording. If you want the literal claim it needs a live run, which is an ask-first on this machine.

Also, per the brief: I'm folding the `miner-rkm` derivation out of `qumbra-wallet`'s `main.rs` into the library so `mine` and `qumbra-wallet miner-rkm` run the same expression (#425's one-derivation rule). `qumbra-faucet` keeps its own copy — it derives at the faucet's own fixed diversifier, it's a separate concern, and I'm reporting it rather than growing this baton.
